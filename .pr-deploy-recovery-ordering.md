Follow-up to #27. Two defects in the recovery work, both caught on the runner.

## 1. `Apply migrations` was broken and redundant

`node node_modules/.bin/prisma` failed immediately:

```
/app/node_modules/.bin/prisma:2
# Resolve $0 through symlinks so basedir is the shim's real directory.
SyntaxError: Invalid or unexpected token
```

`node_modules/.bin/prisma` is a shell shim, not JavaScript, so it cannot be
handed to `node`. The container already does this correctly: `start-docker.sh`
puts `node_modules/.bin` on `PATH`, and `check-db.js` shells out to
`prisma migrate deploy` via `execSync`. The step is removed — the app applies
migrations itself on startup, and duplicating it only risked two concurrent
`migrate deploy` calls against the same database.

## 2. Recovery ran after the app started

The previous order was `Start Umami` → `Recover failed migrations`. Since the
app's startup applies migrations and exits non-zero on `P3009`, the app
crash-looped until one of its automatic restarts happened to land after
recovery. Recovery now runs immediately after PostgreSQL is ready and **before**
the app container is started, so the app applies migrations on its first try.

## Verification

- Full step sequence parsed from the workflow and asserted:
  `Recover failed migrations` precedes `Start Umami`.
- Recovery logic previously verified against a real database poisoned with the
  original broken migration: record marked rolled back, leftover table dropped,
  corrected migration applied, all 28 tables intact, FK referencing
  `website(website_id)`.
- Readiness loop verified against a real PostgreSQL cluster: ready on the first
  attempt once up, retries rather than exiting when the server is not yet
  serving queries.
