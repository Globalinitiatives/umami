feat(replays): optional session summary on public replay links + copy-link column

Two owner-facing improvements to replay sharing, shipped together.

## Public session summary (opt-in)

A shared replay previously showed only the recording. The owner can now also
show the session summary beside it — country, city, device, browser, OS,
language and timings, the same content the owner sees in Replays.

- `SessionReplayShared.showSessionInfo`, `NOT NULL DEFAULT false`. Off by
  default: the summary is the part of a link most worth withholding when the
  recipient is outside the team.
- Set in the `Share replay` modal, and togglable per row in the `Shared` table
  via a new `PATCH` on `/websites/{id}/replays/shared/{replayId}`.
- Toggling updates the share in place. It does not rotate the slug, so a link
  already sent out keeps working.

### The visitor identifier is not part of it

`distinctId` is removed server-side, from the response object itself rather than
hidden by the client, so no request shape can put it back. It is a persistent
cross-session handle: publishing it with a link would turn one recording into a
durable tracking identifier. `SessionInfo` hides the row when it is absent, so a
shared page never shows an empty "Distinct ID" placeholder. The owner view is
unchanged.

The public read is gated on three things, all required:
1. the signed token carries `showSessionInfo`,
2. `canViewSharedReplay` for that exact visit, and
3. the **share row** still has it on.

The row is authoritative on purpose. Trusting only the token meant a link could
not be turned off once issued — a token minted while the summary was on kept
serving the summary until it expired. The visit is also cross-checked against
the replay's own session, so naming a different `sessionId` in the URL returns
404 and never reads that session.

## Copy-link column

A copy icon in the `Shared` table copies the existing public link from the slug
the authenticated owner list already returns. It does not mint, rotate or
re-expose a token, so copying cannot invalidate a link already sent out.

## Reissue after expiry is refused

`createReplayShared` previously upserted, which silently resurrected an expired
or revoked share with a fresh slug — the expiry we told the recipient about
would stop meaning anything. Both states now throw
`ReplayShareClosedError` (HTTP 400) and the row is left untouched.

## Testing

- 26 new tests. The redaction tests are verified to fail when `distinctId` is
  put back, so they are not vacuous.
- Migration 28 replayed from an empty database and on the live-shaped one:
  column is `NOT NULL DEFAULT false`, explicit true/false persist, re-running is
  a no-op.
- Verified end-to-end against real PostgreSQL and a running build: summary
  served without `distinctId`, refuses when off, 404 on another session, 401
  across all website-wide routes.

Pre-existing and untouched: `GET /api/websites` dereferences `auth.user.id`
unguarded, so a share token yields 500 rather than 401. It fails closed (empty
body, no data) and is not caused by this change.
