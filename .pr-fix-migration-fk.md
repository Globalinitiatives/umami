Fixes the failed deploy of #24 (run 36574802228).

## Root cause

Migration `27_add_session_replay_shared` declared its foreign key against the
wrong column:

```sql
REFERENCES "website"("id")
```

The real `website` table's primary key is `website_id`, mapped from the Prisma
field `id`. PostgreSQL rejected the statement:

```
ERROR:  column "id" referenced in foreign key constraint does not exist
```

`prisma migrate deploy` runs at container start (`scripts/check-db.js:111`), so
the failure aborted startup and the app container crash-looped. The health check
then failed with `Container ... is restarting`, which is all the workflow
reported.

## Why it passed review

The migration was originally verified against a hand-built scratch table that
had a literal `id` column, so the constraint test passed against the wrong
schema. Replaying the **full** 27-migration chain against a real PostgreSQL
instance reproduces the failure and the fix.

## Changes

- Correct the FK target to `website("website_id")`.
- On health-check failure, dump the container state and the last 100 lines of the
  application log before exiting. A crash-looping container previously produced
  no diagnostic output at all, which is why this took a local reproduction to
  find.

## Verification

- All 27 migrations replay cleanly against a real PostgreSQL 14 cluster
  (previously 26/27 with `27` failing).
- Against the real schema: 7/7 constraint checks pass — insert against the true
  FK target, unknown-website rejection, unique slug, one share per
  website+visit, non-null `expiresAt`, and cascade delete with the website.
- `tsc --noEmit` and the permission test suite (19/19) unchanged and passing.
