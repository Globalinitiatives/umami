Follow-up to #26.

## Problem

The first attempt at the recovery step failed on its own account:

```
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed:
FATAL:  the database system is starting up
```

`Recover failed migrations` runs immediately after the PostgreSQL container
starts. The app container tolerates this because `scripts/check-db.js` polls
with a real query before proceeding (added in #15), but the new step went
straight to `psql` and hit the `57P03` startup window.

## Fix

Wait for the database to actually serve a query before touching the migration
ledger, using the same reasoning as `check-db.js`: PostgreSQL accepts
connections while initialising and only then refuses queries, so a successful
connect is not a readiness signal. `SELECT 1` is used instead.

The loop was verified against a real cluster both ways: it reports ready on the
first attempt once PostgreSQL is up, and retries rather than exiting when the
server is not yet accepting queries.

## Verification

- Full recovery sequence re-verified earlier against a database poisoned with the
  original broken migration: record marked rolled back, leftover table dropped,
  corrected migration applied, all 28 tables intact, FK pointing at
  `website(website_id)`.
