Unblocks the deploy after the failed migration in #25 (run 36575920095).

## Situation

#25 fixed the foreign key target, but production is already wedged. The first
failed deploy left a row in `_prisma_migrations` with `finished_at` set to NULL
and a half-created `session_replay_shared` table behind it. Prisma now refuses
every migration with:

```
Error: P3009
migrate found failed migrations in the target database, new migrations will not be applied
```

The corrected migration cannot apply until that record is cleared, so this is
not fixable by shipping a better migration alone.

## Changes

- **Recover failed migrations** — before the app starts, mark any migration with
  `finished_at IS NULL AND rolled_back_at IS NULL` as rolled back, then drop the
  tables that migration creates so the corrected version can apply cleanly.
  Table names are read from the migration's own `CREATE TABLE` DDL, not derived
  from the directory name, which does not reliably match (e.g. `16_boards`
  creates `board`, and `22_add_2fa` creates five tables).
- **Apply migrations** — run `migrate deploy` on the runner after recovery, so
  the migration is applied by a step that can report its own failure. Invoked as
  `node node_modules/.bin/prisma` because the image has no `npx`; the existing
  seed step's `npx: not found` was silently masked by its `|| true`.

This makes a bad migration recoverable by a follow-up push instead of requiring
manual access to the production database.

## Verification

Reproduced the exact production failure locally by replaying the original broken
migration, which produced the identical `42703` error and the identical poisoned
ledger state. Then, against that database:

1. The recovery step marks the record rolled back and drops
   `session_replay_shared`.
2. `migrate deploy` with the fixed migration reports **All migrations have been
   successfully applied.**
3. All 28 tables remain present — no unrelated table is dropped.
4. The resulting constraint is
   `FOREIGN KEY (website_id) REFERENCES website(website_id) ON UPDATE CASCADE ON DELETE CASCADE`.

Also confirmed independently: replaying all 27 migrations into a clean database
succeeds, and the replay-share constraints hold (7/7).
