Closes a privilege-escalation hole in replay sharing. A public replay link was
usable as a **full-website credential**.

## The hole

`createReplayShareToken` minted replay tokens with `entityType:
ENTITY_TYPE.website` and a `websiteId`. Every share guard matches a token by
entity id, so a replay token passed them like any website share:

```
canViewWebsiteSection  -> true   (sessions, events, revenue, ...)
canViewSharedWebsite   -> true
canViewSharedWebsiteFilters -> true
canViewWebsite         -> true
canViewBatchWebsites   -> ['website-1']
canViewPixel           -> true
canViewLink            -> true
```

That is 67 API routes — events, metrics, sessions, revenue, breakdown,
retention, goals, realtime, UTM, event-data. Anyone holding a replay share link
could read the entire website's analytics, not just the one recording.

The original 19-test suite passed because it only ever asserted what a replay
token *may* do (`canViewSharedReplay`) and never what it *must not* do. The
negative half of the boundary was untested.

## The fix

A replay token is no longer an entity credential, so it cannot be mistaken for
one:

- `ENTITY_TYPE.replay` (5), distinct from `website`, is set as both `shareType`
  and `entityType` on new tokens. Real share tokens use `shareType`; the old
  `entityType` key is kept so pre-existing tokens stay identifiable.
- New `isReplayShareToken()` recognises a replay token by that type, or — for
  tokens minted before this fix — structurally, by carrying both a `visitId` and
  a `slug`. No other share kind has those, so **links already issued are closed
  by this deploy too**, not just new ones.
- Every guard that matches a token by websiteId/pixelId/linkId now rejects
  replay tokens first: `canViewWebsite`, `canViewBatchWebsites`, `canViewPixel`,
  `canViewLink`, and `canViewWebsiteSection` / `canViewSharedWebsite` /
  `canViewSharedWebsiteFilters` via `shareTokenIncludesWebsite`.

`isReplayShareToken` lives in `permissions/replay-token.ts` because
`share.ts` imports `website.ts`; importing back from the entity guards would be
a cycle.

`canViewSharedReplay` now compares `websiteId` directly instead of going through
`shareTokenIncludesWebsite`, which now rejects replay tokens by design. A replay
link still opens exactly its own recording.

`canViewBoard` was already safe — it only matches `boardId`, which a replay
token never carries — but is asserted in the tests anyway.

## Verification

Probed the real guards before and after. After:

```
canViewWebsite: false   canViewPixel: false   canViewLink: false
canViewBatch:  []       canViewBoard: false
```

New `src/permissions/replay-token.test.ts` (5 tests) covers the whole surface
for both new and pre-fix tokens, and asserts ordinary website/pixel/link shares
are unaffected. It exists as a separate file because `share.test.ts` mocks
`./website` to isolate the share guards.

- `share.test.ts`: 25/25 (6 added, including the negative boundary)
- `replay-token.test.ts`: 5/5
- Full suite: 23 failed / 845 passed — the same 23 pre-existing failures as
  `master`, +12 from the new tests
- `tsc --noEmit`: no new errors
- `biome`: changed files clean (3 remaining findings are pre-existing in
  `team.ts`, `board.test.ts`, `website.test.ts`, which this change does not touch)
